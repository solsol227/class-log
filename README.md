# 클래스로그 (Class Log)

클래스로그는 소규모 학원, 개인 레슨, 동아리형 수업의 운영자와 학생을 위한 모바일 우선 반응형 웹앱입니다. 운영자는 학생별 월간 활동 구성, 일정, 출석, 보강, 수업 피드백을 한곳에서 관리하고, 학생은 자신의 일정과 피드백을 확인하고 답변할 수 있습니다.

현재 저장소는 공모전 시연용 MVP의 개발 기반만 제공합니다. 실제 수강생 데이터는 사용하지 않으며, 로그인과 수업 관리 기능은 아직 연결되어 있지 않습니다.

## 기술 구성

- Next.js 16 (App Router)
- TypeScript
- Tailwind CSS 4
- ESLint
- Supabase JavaScript Client
- Supabase SSR

## 시작하기 전에

컴퓨터에 Node.js와 npm이 설치되어 있어야 합니다. 터미널에서 다음 명령으로 확인할 수 있습니다.

```bash
node --version
npm --version
```

## 설치 방법

저장소를 내려받은 뒤 프로젝트 폴더에서 의존성을 설치합니다.

```bash
npm install
```

## 환경변수 설정

1. 프로젝트 루트의 `.env.example` 파일을 복사합니다.
2. 복사한 파일 이름을 `.env.local`로 변경합니다.
3. 실제 Supabase 프로젝트를 연결할 때만 아래 두 값을 `.env.local`에 입력합니다.

```env
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
SUPABASE_SECRET_KEY=
```

`.env.local`은 Git에 포함되지 않습니다. 실제 키, 비밀번호, 개인정보를 코드나 README에 기록하거나 커밋하지 마세요. 현재 화면 확인에는 Supabase 값이 필요하지 않습니다.

`SUPABASE_SECRET_KEY`는 서버 전용 비밀키이며 브라우저 코드에 전달하거나 노출하면 안 됩니다.

## 개발 서버 실행

```bash
npm run dev
```

터미널에 표시된 주소(기본값 `http://localhost:3000`)를 브라우저에서 열면 됩니다.

확인할 화면은 다음과 같습니다.

- 홈: `/`
- 운영자 로그인 UI: `/login/operator`
- 학생 로그인 UI: `/login/student`

## 코드 검사와 프로덕션 빌드

```bash
npm run lint
npm run build
```

두 명령이 오류 없이 끝나면 기본 코드 품질 검사와 프로덕션 빌드가 정상적으로 완료된 것입니다.

## 현재 구현 범위

- 모바일 우선 홈 화면
- 운영자 로그인 화면 UI
- 학생 로그인 화면 UI
- Supabase 브라우저 클라이언트 생성 함수
- 환경변수 예시와 보안 기본 설정
- 운영자 이메일·비밀번호 로그인
- 학생 닉네임·비밀번호 로그인
- 쿠키 기반 세션 갱신, 보호 경로와 로그아웃
- 입력별 인증 오류, 세션 만료와 권한 오류 안내
- 공통 화면 오류와 404 복구 화면

## 인증 확인

운영자는 Supabase Auth에 등록되고 이메일 확인이 완료된 계정으로 로그인합니다. 학생은 화면에 닉네임을 입력하며, 앱이 정규화된 닉네임을 내부 인증용 가상 이메일로 변환합니다. 학생 직접 회원가입과 계정 생성 기능은 제공하지 않습니다.

로그인 후 이동 경로는 다음과 같습니다.

- 운영자: `/operator`
- 학생: `/student`

두 경로는 로그인 여부와 Supabase Auth JWT의 `app_metadata.role`을 서버에서 확인합니다. 운영자는 `/operator`, 학생은 `/student`만 사용할 수 있으며 다른 역할의 경로에 접근하면 자신의 시작 화면으로 이동합니다. 역할이 없거나 허용되지 않은 계정은 로그아웃 처리됩니다.

## Supabase Dashboard에서 인증 테스트 계정 준비

실제 수강생이나 실제 운영자의 정보는 사용하지 마세요. 아래 절차에서는 이번 시연을 위해 새로 만든 가상 이메일, 닉네임과 강한 테스트 비밀번호만 사용합니다. 계정 정보는 README, 소스 코드, Git 커밋 또는 화면 캡처에 기록하지 않습니다.

### 1. 이메일 확인 설정 확인

1. Supabase Dashboard에서 해당 프로젝트를 엽니다.
2. `Authentication` → `Providers` → `Email`로 이동합니다.
3. 테스트 환경에서 이메일 발송을 사용하지 않을 경우 `Confirm email` 설정을 끕니다. 운영 환경 정책과 함께 쓰는 프로젝트라면 전역 설정을 바꾸지 말고, 아래에서 사용자를 만들 때 이메일 확인 완료 옵션을 사용하세요.
4. 설정을 저장합니다.

### 2. 운영자 테스트 계정 만들기

1. `Authentication` → `Users`에서 `Add user` → `Create new user`를 선택합니다. 초대 이메일을 보내는 메뉴는 사용하지 않습니다.
2. 이번 시연을 위해 새로 만든 가상 이메일과 강한 테스트 비밀번호를 입력합니다.
3. `Auto Confirm User` 또는 이메일 확인 완료 옵션을 켜고 사용자를 만듭니다.
4. 생성한 사용자의 상세 화면에서 `App Metadata` 편집 영역을 엽니다.
5. 기존 `provider`, `providers` 같은 값은 지우지 말고 `"role": "operator"` 필드만 추가한 뒤 저장합니다.

### 3. 학생 테스트 계정 만들기

1. 로컬 개발 서버를 실행하고 `http://localhost:3000/dev/student-auth-email`을 엽니다.
2. 이번 시연을 위해 새로 만든 가상 닉네임을 입력해 내부 인증용 이메일을 생성합니다. 이 개발 전용 도구는 브라우저에서만 변환하며 프로덕션 환경에서는 404를 반환합니다.
3. `Authentication` → `Users`에서 새 사용자를 만들고, 생성된 내부 인증용 이메일과 강한 테스트 비밀번호를 입력합니다.
4. 이메일 확인 완료 옵션을 켜고 사용자를 만듭니다.
5. 사용자 상세 화면의 `App Metadata`에서 기존 값은 유지하고 `"role": "student"` 필드만 추가합니다.

Dashboard 버전에 따라 `App Metadata` 편집 메뉴가 보이지 않을 수 있습니다. 이때 `User Metadata`에 역할을 넣거나 SQL로 Auth 스키마를 직접 수정하지 마세요. 권한이 제한된 서버 전용 Admin API 또는 Edge Function을 다음 단계에서 준비한 뒤 역할을 설정해야 하며, 그때도 secret/service-role 키를 브라우저에 노출하면 안 됩니다.

역할을 바꾼 계정이 이미 로그인 중이라면 로그아웃 후 다시 로그인해 새 JWT를 발급받습니다. 허용되는 역할 문자열은 정확히 `operator`와 `student`뿐입니다.

### 4. 역할 접근 확인

- 운영자 로그인 화면에서 운영자 계정으로 로그인하면 `/operator`로 이동합니다.
- 학생 로그인 화면에서 학생 닉네임과 비밀번호로 로그인하면 `/student`로 이동합니다.
- 어느 로그인 화면을 사용하더라도 로그인 후 서버가 확인한 실제 역할의 경로로 이동합니다.
- 로그인한 운영자가 `/student`를 열면 `/operator`로, 학생이 `/operator`를 열면 `/student`로 이동합니다.
- 역할이 없거나 잘못된 계정은 로그아웃되고 안전한 한국어 안내가 표시됩니다.

권한 판단에는 사용자가 수정할 수 있는 `user_metadata`를 사용하지 않습니다. 현재 단계는 애플리케이션 경로 접근 제어까지만 포함하며, 데이터베이스 테이블과 RLS 정책은 아직 없습니다.

## 인증 오류 안전 검증

실제 계정, 비밀번호, 토큰 또는 쿠키를 조작하지 않고 다음 항목을 확인할 수 있습니다.

- 운영자 로그인에서 이메일을 비우고 제출하면 이메일 입력칸 아래에 안내가 표시됩니다.
- 학생 로그인에서 닉네임을 비우고 제출하면 닉네임 입력칸 아래에 안내가 표시됩니다.
- 비밀번호를 비우면 비밀번호 입력칸 아래에 안내가 표시됩니다.
- 예약된 `.invalid` 도메인의 가상 이메일처럼 실제 계정이 될 수 없는 입력으로 로그인하면 계정 존재 여부를 구분하지 않는 동일한 안내가 표시됩니다.
- 로그인 버튼을 누른 동안 버튼이 비활성화되고 `로그인 중...`으로 바뀝니다.
- 로그아웃 상태에서 `/operator` 또는 `/student`를 열면 해당 로그인 화면으로 이동합니다.
- 존재하지 않는 주소를 열면 404 안내와 홈 이동 버튼이 표시됩니다.

외부 상태가 필요한 오류는 다음과 같이 수동 확인합니다.

- 네트워크 오류: 브라우저 개발자 도구의 Network 탭을 `Offline`으로 바꾼 뒤 로그인하고, 확인 후 즉시 온라인으로 되돌립니다. 토큰이나 쿠키는 수정하지 않습니다.
- 세션 만료: 정상 테스트 계정의 세션이 서버에서 만료된 뒤 보호 경로를 다시 열고 로그인 화면의 만료 안내를 확인합니다. 브라우저 쿠키를 직접 변조하지 않습니다.
- 역할 누락 또는 오류: Supabase Dashboard의 가상 테스트 계정 `App Metadata`에서 역할을 누락하거나 허용되지 않은 값으로 설정한 뒤 새로 로그인합니다. 확인 후 올바른 역할로 복구합니다.
- 교차 접근: 올바른 역할의 가상 테스트 계정으로 로그인한 뒤 반대 역할 경로를 직접 열고, 본인 홈으로 이동한 다음 접근 제한 안내를 확인합니다.
- 일시적인 인증 서버 오류: 테스트 도구에서 인증 요청에 HTTP 5xx 응답을 모의할 수 있을 때만 확인합니다. 실제 프로젝트 설정, 환경변수, 토큰 또는 쿠키를 변경해 오류를 만들지 않습니다.
- 공통 화면 오류: 유지보수용 테스트 환경에서 예외를 발생시키는 별도 테스트가 준비된 경우에만 확인합니다. 운영 코드에 오류 우회 경로나 고의 예외를 남기지 않습니다.

오류 화면과 콘솔에는 Supabase 원문 오류, 내부 오류 코드, 내부 인증 이메일, 사용자 ID, JWT 또는 환경변수 값이 표시되지 않아야 합니다.

- 업무 데이터에 대한 역할별 RLS 정책
- 학생 관리
- 일정, 출석, 보강, 피드백 관리
- 데이터베이스 테이블과 SQL
- 파일 업로드
- 실제 데이터 또는 더미 학생 데이터
- 배포 설정
