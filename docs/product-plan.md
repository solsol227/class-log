# Class Log 제품 기획

## 한 줄 요약

학생이 프로그램을 이용하는 전체 흐름 — **학생 관리 → 일정 배정 → 출결 → 보강 → 피드백 → 대화** — 을 한 곳에서 관리하는 운영 도구.

## 문제 정의

Class Log의 목적은 단순히 수업 일정을 저장하는 것이 아니다.

운영자는 학생마다 다른 프로그램과 일정, 배정 변경, 출결, 보강, 피드백을 함께 관리해야 한다. 이 정보가 여러 화면이나 메모에 흩어지면 다음 문제가 생긴다.

- 어떤 학생이 현재 어떤 프로그램을 이용 중인지 바로 알기 어렵다.
- 확정 전 일정과 실제 일정이 섞일 수 있다.
- 학생 배정 변경 이력이 사라질 수 있다.
- 보강이 필요한 학생을 놓칠 수 있다.
- 수업 피드백과 이후 대화가 분리되지 않는다.
- 실제 수업 담당자와 시스템에 내용을 입력한 사람이 다를 수 있다.

Class Log는 이 흐름을 학생 단위로 연결해 운영자가 반복 관리해야 하는 일을 줄이는 것을 목표로 한다.

## 주요 사용자

### 운영자

- 학생과 프로그램을 관리한다.
- 일정을 만들고 학생을 배정한다.
- 출결을 기록한다.
- 필요한 경우 보강을 생성하고 일정을 배정한다.
- 피드백을 작성하거나 실제 피드백 제공자를 기록한다.
- 직원/담당자 정보를 관리한다.

### 학생

- 자신의 확정 일정만 본다.
- 자신의 출결·피드백 등 허용된 정보만 본다.
- 게시된 피드백에 댓글/답글로 대화할 수 있다.

## 제품 원칙

1. **운영자의 수동 관리 업무를 줄인다.**
   - 자동 계산 가능한 상태는 자동 계산한다.
2. **과거 기록을 보존한다.**
   - 배정 해제, 프로그램 중단, 과거 피드백 이력을 이유 없이 삭제하지 않는다.
3. **임시 계획과 확정 정보를 구분한다.**
   - Draft 일정은 운영자에게만 보인다.
4. **한 정보를 여러 곳에서 중복 관리하지 않는다.**
5. **학생에게는 본인에게 필요한 정보만 노출한다.**
6. **데이터 무결성은 UI뿐 아니라 서버/DB에서도 보호한다.**
7. **아직 필요성이 명확하지 않은 구조는 미리 만들지 않는다.**

# 1. 학생 관리

## 기본 정보

학생은 다음 정보를 관리할 수 있다.

- 이름/닉네임
- 성별
- 나이
- 전화번호
- 유입경로
- 가입월
- 특이사항

## 이름/로그인 식별자

별도의 표시 이름을 두지 않는다.

**nickname 하나를 로그인 식별자와 화면 표시 이름으로 동일하게 사용한다.**

## 나이

숫자로 입력하며 허용 범위는 1~119세다.

## 유입경로

통계를 위해 자유입력 대신 다음 선택값을 사용한다.

- 인스타그램
- 당근
- 지인소개
- 네이버

## 가입월

Class Log 등록일과 실제 이용 시작월은 다를 수 있으므로 가입월은 별도로 기록한다.

---

# 2. 학생 프로그램

학생은 여러 프로그램을 동시에 또는 시기별로 이용할 수 있다.

프로그램:

- 평일보컬
- 주말보컬
- 대여
- 체험

## 프로그램 이력

같은 프로그램을 중단했다가 다시 시작할 수 있다.

예:

- 평일보컬: 2026.03 ~ 2026.07 / 중단
- 평일보컬: 2026.09 ~ / 진행중

과거 이력은 유지하되 같은 학생에게 같은 프로그램이 동시에 여러 건 진행중이 되지는 않게 한다.

## 저장 상태

- 진행중
- 중단

## 중단 사유

선택적으로 기록한다.

- 잠시 쉼
- 이용 종료
- 기타

## 비활성

비활성은 운영자가 직접 지정하는 상태가 아니다.

진행중 프로그램이라도 관련 일정 배정이 약 3개월 동안 없으면 시스템이 자동으로 비활성으로 판단한다. 새로운 관련 일정이 배정되면 다시 진행중으로 판단한다.

---

# 3. 일정

## 프로그램

일정 하나는 하나의 프로그램에 속한다.

일반 수업 일정에서 사용하는 프로그램:

- 평일보컬
- 주말보컬
- 체험

대여는 일반 lesson 일정에 넣지 않는다.

## 학생 배정

- 한 일정에는 여러 학생을 배정할 수 있다.
- 한 학생은 여러 일정에 참여할 수 있다.
- 같은 학생을 같은 일정에 중복 배정할 수 없다.
- 배정 해제는 과거 기록을 지우지 않는다.
- 같은 일정에 다시 배정하면 기존 배정 기록을 재활성화한다.

## Draft 일정

Draft는 아직 학생에게 확정되지 않은 운영자 내부 일정이다.

Draft에서도 다음을 변경할 수 있다.

- 날짜
- 시간
- 학생
- 제목
- 메모
- 담당자

학생에게는 Draft가 보이지 않는다.

확정하면 일반 일정으로 전환한다.

## 시간 충돌

Draft에 학생이 배정된 경우에도 그 시간은 임시로 점유된 것으로 본다.

같은 학생을 시간이 겹치는 다른 Draft/확정 일정에 중복 배정할 수 없다.

종료시간과 다음 일정 시작시간이 같은 것은 허용한다.

예:

- 17:00~18:00
- 18:00~19:00

가능.

---

# 4. 출결

현재 출결 상태:

- 출석
- 결석
- 사유결석

한 학생과 한 수업의 최종 출결 상태는 하나만 존재한다.

최초 출결 기록 시각은 별도로 보존한다. 출결을 나중에 수정해도 최초 기록 시각은 바뀌지 않는다.

---

# 5. 보강

보강은 단순한 일정 속성이 아니라 **처리해야 할 운영 업무**로 본다.

흐름:

**보강 발생 → 보강 대기 → 일정 배정 → 보강 예정 → 완료**

## 보강 대기

최소 다음 정보를 보여준다.

- 학생
- 원래 수업
- 사유
- 발생일
- 상태
- 일정 배정

## 일정 배정

두 방법을 지원한다.

- 기존 일정에 학생 배정
- 새 일정 생성

## 완료

가능하면 연결된 보강 일정의 실제 출결 결과와 연동해 완료 처리한다.

## 중복 방지

한 학생과 한 원수업에 동시에 열린 보강은 한 건만 허용한다.

완료·취소된 과거 보강은 이력으로 남긴다.

## 프로그램 일치

보강은 원수업과 같은 프로그램으로 제공한다.

프로그램 내부의 더 세부적인 활동 유형은 실제 필요가 명확해질 때 별도로 설계한다. 현재는 `activity_type`을 만들지 않는다.

---

# 6. 피드백

피드백은 특정 수업과 학생에게 연결되는 공식 기록이다.

한 학생+한 수업에 여러 피드백을 만들 수 있다.

운영자는 피드백을:

- 추가
- 수정
- 삭제
- 게시

할 수 있다.

삭제는 기록 보존을 위해 soft-delete를 우선한다.

## 실제 제공자와 입력자

피드백을 실제로 제공한 사람과 Class Log에 입력한 사람은 다를 수 있다.

예:

보컬트레이너가 피드백 제공
→ 매니저가 Class Log에 입력

두 역할은 구분해서 기록한다.

## 학생 공개

학생은 다음 조건을 만족하는 자기 피드백만 볼 수 있다.

- 자기 수업과 연결
- 게시됨
- 삭제되지 않음
- Draft 일정이 아님

---

# 7. 피드백 댓글/답글

- 피드백 = 공식 기록
- 댓글 = 피드백 이후 대화

학생과 운영자는 피드백 아래에서 댓글과 답글을 이어갈 수 있다.

다른 피드백의 댓글을 잘못 parent로 연결할 수 없어야 한다.

---

# 8. 직원 / 담당자

인증 권한의 큰 구분은 계속 다음을 유지한다.

- operator
- student

업무상 역할은 별개다.

- 매니저
- 보컬트레이너

직원은 반드시 로그인 계정을 가질 필요가 없다.

한 수업에는 여러 담당자를 연결할 수 있다.

예:

- 진행 담당: 매니저
- 전문 피드백 담당: 보컬트레이너

직원이 실제 Class Log에 로그인해야 할 필요가 생기면 그때 세부 권한을 별도로 설계한다.

---

# 9. 월간 활동

기존 월간 활동 계획 기능은 유지한다.

- 활동 항목은 사용자가 보는 명시적 순서를 유지한다.
- 학생 연결 정보는 기존 데이터 무결성과 RLS에 사용되므로 유지한다.

---

# 10. 향후 기능

## 학생 계정 관리 전용 페이지

이번 구현 범위에는 포함하지 않는다.

향후 별도 화면에서 다음을 검토한다.

- 로그인 정보 관리
- 계정 전달 상태
- 비밀번호 재설정
- 로그인 접근 중지/재활성화

현재 학생 생성 시 Supabase Auth 계정과 학생 데이터가 함께 생성되는 흐름은 유지한다.

보안 원칙:

- 기존 비밀번호를 다시 보여주지 않는다.
- 평문 비밀번호를 public DB에 저장하지 않는다.
- 평문 비밀번호를 로그에 기록하지 않는다.

## 대여 예약

`대여`는 학생 프로그램으로 유지할 수 있지만 일반 보컬 수업 일정과 분리한다.

실제 예약 일정은 향후 별도 예약 도메인으로 설계한다.

## 현재 의도적으로 만들지 않는 것

- 학생 계정 관리 전용 페이지
- 대여 예약
- 세부 activity type
- 프로필 이미지
- 과도한 직원 권한 세분화

# 현재 구현 이후 우선 개선

## 운영 UX
- 직원 수정/삭제
- 직원 활성 상태 UX 단순화
- 보강 수정/삭제
- 로그인 페이지 뒤로가기

## 사유결석 기반 보강
현재의 수동 보강 등록을 향후 다음 흐름으로 개선한다.

**사유결석 → 보강 가능 건 → 보강 대기 → 일정 배정 → 완료**

같은 사유결석에서 중복 보강이 생기지 않아야 한다.

## 학생 일정 상세
학생의 `내 일정`에서 일정 하나를 클릭하면 상세 페이지로 이동한다.

상세에는 일정 정보, 담당자, 본인 출결, 게시된 피드백과 댓글을 보여주는 방향으로 확장한다.
